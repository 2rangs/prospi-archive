## 근거 1 — 값이 카드를 따라가지 않는다

坂本 勇人: 2016~2026 **48장 전부** 미트 40 / 파워 53 / 주력 57.
같은 기간 포구는 63 → 60 → 72 → 70 → 61 → 65 → 74 로 카드마다 바뀐다.

菊池 涼介: 43장 전부 미트 45 / 파워 56 / 주력 72. 포구는 80 → 96 → 94 → 87 → 84.

## 근거 2 — 추출 코드가 서로 다른 테이블을 읽는다

`tools/generate_site_cards.py` 118–137행:

```python
player = players.get(player_id)          # 선수 테이블 (선수당 1행)
base = {"meetR": (word >> 4) & 0x7F, ...}   # <- 여기서 미트/파워/주력
max_speed = ((pitcher_word >> 7) & 0x7F) + 80

master = master_for_file.get(image["resource_file"])   # 카드 마스터 (카드당 1행)
defense = {"catching": master["u32_0xe0"], ...}        # <- 여기서 포구/송구/어깨
```

미트·파워·주력·구속·스태미나는 **선수 마스터**에서, 포구·송구·어깨는 **카드
마스터**에서 온다. 그래서 전자는 카드가 달라도 안 변한다.

## 추가 위험 — 카드 마스터 매칭이 비례식 추정이다

같은 파일 95행:

```python
master_index = round(index_image * (len(masters) - 1) / max(1, len(images) - 1))
```

이미지 순번을 마스터 순번에 **비례로 밀어 넣는** 방식이라 실제 조인이 아니다.
수비 값이 카드마다 변하는 것까지는 맞지만, **어느 카드에 붙는지**는 보장되지
않는다. 위 표에서 포구 84 vs 81, 송구 85 vs 77 의 차이가 여기서 나올 수 있다.

## 능력 워드의 실제 구조 (역어셈블로 확정)

**여섯 스탯이 하나의 64비트 워드에 있다.** `libAll.so` 의 게터 여섯 개가 모두
`PlayerAbility+0x18` 을 읽는다.

```
GetMeet      ldr w8,[x0,#0x18]   ubfx #4,#7   /  ubfx #11,#7   ; 미트 우 / 좌
                                 HANDER 2 -> (우 + 좌) x 0.5    ; 표시 미트 = 평균
GetPower                         ubfx #18,#7
GetRunning                       lsr  #25
GetShoulder  ldr w8,[x0,#0x1c]   and  #0x7f                    ; 비트 32-38
GetThrowing  ldr x8,[x0,#0x18]   ubfx #39,#7                   ; 비트 39-45
GetCatching                      ubfx #46,#7                   ; 비트 46-52
```

| 비트 | 항목 |
| --- | --- |
| 4-10 / 11-17 | 미트(우) / 미트(좌) — 표시값은 둘의 평균 |
| 18-24 | 파워 |
| 25-31 | 주력 |
| 32-38 | 어깨 |
| 39-45 | 송구 |
| 46-52 | 포구 |
| 53-59 | 미상 (값 50~70대) |

**[검증]** 坂本 勇人 선수워드를 풀면 포구 74 / 송구 69 / 어깨 79 로 카드 마스터
2026 카드값과 **정확히 일치**한다. 菊池 涼介는 포구 84 / 어깨 76 일치.

즉 `players.csv` 의 워드 하나에 공격·수비가 **같이** 들어 있었고, 우리는 하위
32비트(공격)만 읽고 상위 32비트(수비)를 버리고 있었다.

## 守備適性 워드 — 통째로 놓치고 있었다

**[확인된 사실]** `PlayerAbility::GetDefense(bbdefine::POS)` (0x463b47c) 는 능력
워드가 아니라 **`+0x10` 의 다른 64비트 워드**를 읽는다. 점프테이블
(0x1f67514 = `[0,9,13,17,21,25,29,33,37]`)을 풀면 포지션 9개가 한 워드에 있다.

| 비트 | 포지션 |
| --- | --- |
| `ldrb [x0,#0x20]` | 투수 |
| 4-10 / 11-17 / 18-24 / 25-31 | 포수 / 1루 / 2루 / 3루 |
| 32-38 (`ldrb [x0,#0x14]`) | 유격 |
| 39-45 / 46-52 / 53-59 | 좌익 / 중견 / 우익 |

능력 워드가 `+0x18` 이므로 적성 워드는 `+0x10`, 즉 **선수 레코드 오프셋 0** 이다.

**[검증]** 실제 수비 포지션과 전부 일치한다.

| 선수 | 디코드 | 실제 |
| --- | --- | --- |
| 菊池 涼介 | 2루 63 | 히로시마 2루수 (레퍼런스 카드 二 68) |
| 坂本 勇人 | 3루 52 · 유격 46 | 유격 → 3루 전향 |
| 大谷 翔平 | 좌익/중견/우익 42 · 투수 3 | 외야수 겸 투수 |
| 山川 穂高 | 1루 56 | 1루수 |
| 筒香 嘉智 | 1루 34 · 3루 42 · 좌익 42 · 우익 40 | 코너 내야/외야 |

**[신뢰도] CONFIRMED** (역어셈블 + 표본 전부 일치)

**[정정]** 처음에 투수 적성을 레코드 `0x18` 에서 읽었는데 틀렸다. 레코드 기준
오프셋은 `PlayerAbility 오프셋 − 0x10` 이므로 `+0x20` 은 **레코드 0x10** 이다.
바로잡으니 大谷 翔平 58 · 山本 由伸 81 · 田中 将大 66 처럼 값이 제자리를 찾았다.

**[확인된 사실] 투수와 야수는 완전히 갈린다.** 2,821명이 투수만 1,384 ·
야수만 1,375 · **둘 다 62** 로 나뉘고 둘 다 0 인 선수는 **0명**이다. 투타겸업
62명은 게임에서도 타자 카드와 투수 카드가 따로 나오므로, 카드 유형에 맞는
적성만 남긴다 (大谷 타자 카드 → 좌익/중견/우익 42, 투수 카드 → 투수 58).

**[부수 발견] 카드 유형 판정이 틀려 있었다.** `player_type` 을 구종 데이터
유무로만 정하다 보니 구종이 비어 있는 **투수 카드 344장**(山本 由伸 · 平野 佳寿
등 2026 var0500 계열)이 타자로 분류돼 있었다. 적성 워드를 보조 신호로 넣어
고쳤다 — 투수 카드 5,522 → **5,866장**.

**[처리]** `unpack_aptitude()` 로 뽑아 카드 **12,252장(80%)** 에 `aptitude` 를
넣고 상세 페이지에 "수비 적성" 블록으로 표시한다.

**[정정]** 앞서 "능력 워드 비트 53-59 는 미상, 적성 가설은 상관계수로 볼 때
약하다" 고 적었던 것은 **틀렸다**. 적성은 실재했고 다만 **다른 워드**에 있었다.
상관계수로 성격을 추정하려 한 접근 자체가 잘못이었고, 게터를 먼저 열거해
역어셈블했어야 했다. 능력 워드(+0x18) 의 비트 53-59 는 여전히 미상이다.

## 카드별 공격 능력치는 다운로드 데이터에 없다

카드 마스터(`CARDMASTERDATA.CHK`, 압축 없음, 레코드 236B)는 수비 3개를 **plain
u32** 로 따로 들고 있고(+0xe0/e4/e8) 공격 자리는 없다. 그 값은 선수워드와
포구 70% · 송구 73% · 어깨 48% 만 일치하므로 **카드별 덮어쓰기**가 맞다.

목표 워드를 조립해 전수 탐색했지만 없다:

| 조건 | CARDMASTERDATA | CONPLAYERDATA | PLAYERDATA |
| --- | --- | --- | --- |
| 파워61 · 주력67 · 미트평균60 (菊池 Lv0) | 0 | 0 | 0 |
| 파워68 · 주력75 (菊池 MAX) | 0 | 0 | 0 |
| 64비트: 포구84 · 송구85 · 어깨76 | 0 | 0 | 0 |
| 선수워드 기준 델타(+64 바이어스) | 0 | 0 | 0 |

**[해석]** 카드별 공격 능력치는 서버가 런타임에 준다. ANSS 문서 2절의 "카드별
effect id 는 서버가 주는 `PlayerCardMinInfo` 값" 과 같은 구조다.
**[신뢰도] CONFIRMED (전 파일 탐색)**

## 고치려면

1. 카드 마스터에서 공격 능력치 오프셋을 찾는다(현재는 `u32_0xe0/0xe4/0xe8`
   세 개만 쓰고 있다). 같은 레코드 안에 미트/파워/주력이 있을 가능성이 높다.
2. 이미지 ↔ 카드 마스터를 비례식이 아니라 실제 키로 조인한다.
3. 특훈 Lv 성장표·스피리츠·탄도·특수능력·수비적성은 별도 테이블을 찾아야 한다.


## 2015 카드의 타자/투수 구분 — 판정 불가

**[확인된 사실] 2015 파일명은 `CS{그룹1}{변형2}{구단3}{슬롯·카드3}` 이다.**

| 자리 | 뜻 | 근거 |
| --- | --- | --- |
| 1 | 그룹(=1, 2015) | 전수 |
| 2-3 | 카드 변형/계열 (01 703장 · 51 56 · 07 49 …) | 전수 |
| 4-6 | 구단 (010·020…120 과 011·021…121 의 24종) | 코드별 선수 명단이 실제 구단과 일치 |
| 7-9 | 구단 내 슬롯 + 카드번호 | 中田翔 13·14·15 · 大谷翔平 23·24·25 · 宮西 31·33 |

슬롯은 등번호 순으로 보인다(中田 6 → 大谷 11 → 宮西 25).

**[반박된 가설 1] 구단코드 끝자리가 투수/야수 구분이다.**
→ 연결된 1,123장이 **전부 끝자리 0** 이다. 홀수 코드는 미연결 208장 쪽이다.

**[반박된 가설 2] 변형 2자리가 유형을 담는다.**
→ 투수 비율이 01 44% · 07 76% · 21 11% 로 흩어진다. 카드 계열 코드지 유형이 아니다.

**[반박된 가설 3] 슬롯 번호대가 투수/야수를 가른다.**
→ 구단 080 의 슬롯순 유형열이 `FFFFFFPPPFFFPPPPPPPPPPPPPFFF…` 로 뒤섞인다.
   투수 번호 중앙 162 · 야수 182 로 겹친다.

**[반박된 가설 4] 카드 이미지 OCR 에 포지션이 찍혀 있다.**
→ 1,331장 중 1,319장에 OCR 이 있지만 내용은 연도 · 시리즈명 · 선수명뿐이다.
   `投手/捕手/外野` 같은 단어 출현 **0회**. 라틴 토큰은 구단 로고 오독이다
   (SAKUTEN/SAGLE = 楽天イーグルス, GINJI = 銀次).

**[해석]** 2015 카드는 카드 마스터 레코드 자체가 없어서(그래서 원래 코드가
`if group > 1` 로 걸러 냈다) 카드별 유형 정보가 어디에도 없다. 선수 적성으로
추론하는 것이 유일한 방법이고, 투수 적성만 있으면 투수 · 야수 적성이 있으면
타자로 둔다.

**[남는 오차]** 투타겸업 선수만 갈린다. 데이터상 투타겸업은 **大谷 翔平 1명**,
해당 2015 카드는 **6장**(전체 15,222장의 0.04%)이다. 현재 전부 타자로 배정돼
있는데 2015년 그는 주로 투수였으므로 이 6장은 틀렸을 수 있다.
**[신뢰도]** 파일명 구조 CONFIRMED · 유형 판정 불가 CONFIRMED (신호 4개 전부 음성)
