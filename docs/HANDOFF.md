## 이번 세션에서 확정한 것 (r96)

### [확인된 사실] ADVANCE 는 "중복 배치"가 아니라 순차 발사 위상이다
한 부모 아래 같은 클립을 참조하는 인스턴스 묶음의 ADVANCE 값은 그 클립의
`len−1` 을 인스턴스 수 N 으로 **균등 분할**한다.

| 클립(1285005) | len | 사본 | ADVANCE | 검산 |
|---|---|---|---|---|
| round_03 | 61 | 12 | 5,10,…,55 | 12×5=60=len−1 |
| outsideflame | 41 | 4 | 10,20,30 | 4×10=40 |
| tubu01 | 91 | 3 | 30,60 | 3×30=90 |
| tububase | 361 | 2 | 180 | 2×180=360 |
| fan02_02 | 31 | 3 | 10,20 | 3×10=30 |

- **[근거]** 파일 250개 전수. 서로 다른 ADVANCE 를 2개 이상 가진 인스턴스 묶음 3,150개 중
  2,246개(**71.3%**)가 정확히 `(len−1)/N` 간격. 나머지 28.7% 도 `[0,3,6]`,
  `[2,20,25,30,33]` 처럼 손으로 다듬은 **단조 증가** 시차. "중복"으로 볼 값은 0건.
  `_t`/`_u` 반쪽 쌍은 **같은** ADVANCE 를 공유하므로 서로 다른 값만 세어야 한다.
- **[해석]** N 개 사본을 한 주기에 걸쳐 차례로 발사시키는 장치. 로고 반짝임
  캐스케이드도 같은 원리(빛이 사본을 타고 흐른다).
- **[처리]** `public/effects/no-advance.json`(390효과·3,758파트명) 삭제,
  `advOff()`/`noAdvTable` 제거, `const own = advanceScale * (part.user ?? 0);` 로 단순화.
  A/B 토글 `window.__anssAdvance = 0` 만 남김.
- **[실패 이력]** r86·r91·r93·r94 는 이 시차를 "중복"으로 보고 껐다. 지우면 N 개가
  **동시에** 발사돼 사방으로 퍼진다 — 사용자가 반복 지적한 "사방팔방에서 날아온다 /
  계속 흩어진다" 가 바로 그 증상. 원인과 처방이 뒤집혀 있었다.
- **[신뢰도]** CONFIRMED (전수 측정)

### [확인된 사실] r95 — UV 창 0→1 재작성 철회 (직전 작업, 사용자 개선 확인)
`evaluate.ts` 가 모든 `uvsx`/`uvsy` 키의 값 0 을 1 로 **덮어쓰고** 있었다(23,813키).
"수축해 사라지는" 애니메이션이 통째로 지워졌다.
- 근거: uvs=0 키 중 투명/숨김 6,812 제외 후 **11,993(70.5%)이 기하 스케일도 0**

## `/vroad` 3D 타석 프로토타입

- 위치: `app/vroad/page.tsx`
- 로컬 확인: `http://localhost:3000/vroad` (개발 서버 실행 상태 전제)
- 네이티브 프로스피 엔진을 옮긴 것이 아니라 Three.js로 새로 만든 타석 프로토타입이다.
  선수 표현은 실제 CL 카드아트 빌보드이고, 물리·판정 입력은 실제 카드 스탯을 사용한다.
- 씬: 하늘 셰이더, 줄무늬 잔디, 내야 흙 다이아몬드, 파울라인, 펜스, 관중석,

- 데이터: `/data/cards.json`에서 파워가 좋은 타자와 구종이 많은 투수를 자동 선택한다.

- 투구 물리: 구속→비행시간, 구종 화살표→변화 방향, 구종 파워→변화량, 중력→낙차.
- 타구 물리: 파워→타구 초속→포물선→비거리, 결과는 홈런/안타/플라이/땅볼.
  홈런이면 카메라가 타구를 추적한다.
- 타격 판정: 미트 커서의 크기와 타이밍 허용창은 미트 스탯에 연동하며,
  커서-공 거리와 타이밍을 함께 사용해 헛스윙/컨택 품질을 정한다.
- 조작: 투구 후 마우스로 미트 커서를 맞추고, 플레이트 도달 시 Space 또는 클릭으로 스윙.
- HUD: 양 선수 카드/스탯, B/S/O, 타석·안타·HR, 구종, 결과 오버레이, 플레이 로그.

## 원본 수비 스탯 화면 분석 (진행 중, 2026-09-01)

### 확정

- 직전 구현에 쓴 `PE_BG02/001_IMAGE001_512x1024.png`는 수비 스탯 배경이 아니다.
  선수 상세용 세로 경기장 배경이며, 여기에 임의 SVG 다이아몬드를 얹은 구현은 오답이다.
- 네이티브 클래스 `CardStatusDisp`가 실제 선수 상세 화면을 만든다.
- `CardStatusDisp` 생성자(`libAll.so` VA `0x3d551c8`)는 `MenuChunkLoad::GetChunkLoad(2)`를
  호출한 뒤 `CreateFitSBS(..., "ETC_pinfo_bg_h", ...)`로 상세 배경 surface를 생성한다.
- 같은 바이너리에 다음 원본 surface 이름이 확인된다.
  `ETC_pinfo_bg_h`, `ETC_pinfo_sub_f1_f`, `ETC_pinfo_sub_f1_waku`,
  `ETC_pinfo_sub_f2_b`, `ETC_pinfo_sub_f3_d`, `ETC_pinfo_sub_f4`,
  `ETC_pinfo_sub_abi01`, `ETC_pinfo_sub_abi02`, `ETC_pinfo_btn_onoff` 등.
- `MenuChunkLoad` 초기화 테이블 순서는 `MENU2D.CHK`, `BBMENU.CHK`, `SELECT2220.CHK`, ...이며,
  enum 값 2는 `SELECT2220.CHK`다. 따라서 수비 상세 화면의 원본 surface 정의는
  `SELECT2220.CHK`를 우선 분석해야 한다.
- 단순 PNG 시그니처 추출은 atlas 원본만 꺼내므로 `ETC_pinfo_bg_h` 같은 surface 조립 결과를
  직접 제공하지 않는다. CHK의 surface/셀 좌표를 해석해 atlas에서 정확히 잘라 조립해야 한다.

### 기각

- `FIELDER2.CHK`는 이름만 보고 수비 UI 후보로 삼으면 안 된다. RDI에서 약 10.9MB인 대형
  리소스로 확인되어 3D 야수 리소스일 가능성이 높고, `CardStatusDisp`의 실제 로딩 경로와도 다르다.
- 경기장처럼 보이는 배경을 색상/분위기로 골라 대체하지 않는다.
