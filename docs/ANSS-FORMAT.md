# 프로스피A ANSS 카드 이펙트 포맷

`ANSS_EF_*.CHK` 하나를 원본 런타임과 같은 규칙으로 재생하기 위해 바이너리
(`libAll.so`, arm64-v8a, 86.8MB)와 682개 이펙트 파일에서 확인한 내용이다.
각 항목은 [확인된 사실] / [근거] / [신뢰도]로 적었고, 확정하지 못한 필드는
`UNKNOWN_<offset>`으로 남겼다. 추측을 사실처럼 적지 않는 것이 이 문서의 규칙이다.

신뢰도: **CONFIRMED**(바이너리 코드 또는 전수 데이터로 확정) ·
**STRONG**(데이터 다수로 검증, 반례 없음) · **POSSIBLE**(정합적이지만 대안 존재) ·
**WEAK**(추정) · **REJECTED**(반증됨)

---

## 1. 컨테이너

| 항목 | 값 | 신뢰도 |
| --- | --- | --- |
| CHK = Chunk 컨테이너, 로더 클래스 `ChunkLoad` | 태그 + 길이 반복 | CONFIRMED |
| `CLMP` 섹션 | PNG 텍스처 시트 1장 | CONFIRMED |
| `PRCT` 섹션 | AnimSS 파트 1개(셀맵 + 클립 + 노드 + 키프레임) | CONFIRMED |
| `CMP` 섹션 | 압축 블록. 알고리즘 미확인 | UNKNOWN |

파일명은 `ANSS_EF_%06d_L.CHK` / `ANSS_EF_%06d_S.CHK` 포맷으로 **정수 하나**에서
만들어진다. `_L`은 큰 카드, `_S`는 작은 카드용. [근거] `strings libAll.so`.
[신뢰도] CONFIRMED

## 2. effect id 구조

`group + series(2) + sub(2) + rank(1)`. group 1~9는 6자리, 10~12는 7자리.

| 자리 | 뜻 | 근거 | 신뢰도 |
| --- | --- | --- | --- |
| group | 카드 연도 그룹(1=2015 … 12=2026) | 카드 `group` 필드와 값 범위 일치 | STRONG |
| series | 카드 종류 계열 | 카드 `variant` 앞 2자리와 18종 겹침 | POSSIBLE |
| sub | 같은 series 안의 연출 변형(00~07, 10, 13, 14, 20) | 682개 파일명 전수 | STRONG |
| rank | 카드 등급 | rank 3 → 스프라이트 평균 8.0장, 4 → 14.8장, 5 → 16.6장 단조 증가 | CONFIRMED |

카드별 실제 effect id는 서버가 주는 `carddef::PlayerCardMinInfo` 값이며
(`AnalyzeHttpData` 계열 파서가 채운다) 로컬 11,936개 파일 어디에도 표가 없다.
[신뢰도] CONFIRMED (없다는 사실)

### 3.1 스테이지가 표시 프레임이다

**[확인된 사실]** 스테이지는 이펙트마다 다르다(682개 전수).

| stageW × stageH | 개수 |
| --- | --- |
| 720 × 1136 | 350 |
| 720 × 1484 | 208 |
| 640 × 1136 | 102 |
| 720 × 1386 | 18 |
| 740 × 1136 | 3 |
| 640 × 1484 | 1 |

**[근거]** `tools/export_anim.py` 604행이 애니 레코드 `+0x58`의 float 2개를
`stageW/stageH`로 이미 뽑아 두었다. 반대로 clip 의 canvas 는 682개 전부
320×320 이라 이펙트를 구분하지 못한다.

**[해석]** 기준 화면(640×1136)으로 고정해 그리면 579개(85%)가 가로로,
209개(31%)가 세로로 잘린다. 알파가중 면적으로 재면 프레임 안에 들어오는
비율이 중앙값 **65.9%** 밖에 안 됐다. 자기 스테이지를 쓰면 71.8% 로 오른다.

**[경쟁 가설]** "스테이지 밖이 잘리는 게 문제이니 1.5배로 넓히면 된다."
→ **REJECTED**. 불투명 대형판 500개를 재보니 가로가 스테이지의 0.95~1.20 배에
42% 가 몰린다(1213005 `bg_kage_color` 726 / 720 = **1.01**). 스테이지 폭에 딱
맞춰 그린 배경판이 실재하므로, 캔버스를 넓히면 그 판의 사각 경계가 드러난다
(1152055 `bg_base` 768 · `black_3` 640 이 그 예다). 즉 스테이지 = 화면이고
게임도 여기서 자른다. 밖으로 날아간 파티클이 안 보이는 건 원본도 마찬가지다.

**[교차검증]** 인게임 스크린샷(有原 航平)에서 역산한 불꽃/카드아트 비는
860/568 = **1.51**. 스테이지 폭 720 을 쓰면 720/512 = **1.406** 으로 7% 차이고,
640 을 쓰면 1.25 로 17% 차이다. 파일에서 읽은 값이 스크린샷 쪽으로 붙는다.

**[아직 모르는 것]** 스테이지 안에서 카드 아트가 몇 배로 그려지는지. 이펙트
안에는 카드 자리를 뜻하는 파츠도, 400×500 이상 셀도 **없다**(전수 확인). 이
값은 앱 UI 쪽에 있고 아직 못 찾았다.

**[신뢰도]** CONFIRMED (스테이지 필드) · STRONG (스테이지 = 화면)

## 4. 시간

| 필드 | 값 | 뜻 | 신뢰도 |
| --- | --- | --- | --- |
| 클립 `+0x40` | 항상 30 | fps | STRONG |
| 클립 `+0x44` | 항상 11 | `UNKNOWN_clip44` | UNKNOWN |
| 애니 `+0x48` | 항상 30 | fps | CONFIRMED |
| 애니 `+0x4c` | 31~4800 | **프레임 수** = 최대 키프레임 + 1 | CONFIRMED |

애니메이션마다 길이가 다르고(121, 361, 601 …), 인스턴스로 끌어온 서브
애니메이션은 자기 길이로 감긴다. 클립의 30을 길이로 쓰면 대부분의 애니메이션이
앞 12%만 반복된다. [근거] 60개 이펙트 888개 애니메이션 전수 집계.

`USERDATA`(attr 30) 문자열 — 30개 이펙트 전수 수집 결과 4종:

| 문자열 | 붙는 위치 | 뜻 | 개수 | 신뢰도 |
| --- | --- | --- | --- | --- |
| `[LOOP]` | 클립 루트(kind 0) 0프레임 | 이 클립은 반복 | 967 | STRONG |
| `[ADVANCE]#N` | 인스턴스(kind 3) 0프레임 | 그 인스턴스 타임라인을 N프레임 앞으로 | 991 | CONFIRMED |
| `[ANIME]#파트:클립:애니` | kind 0 노드, iclip 없음 | **다른 PRCT 파트**의 애니메이션을 그 자리에 재생 | 352 (100개 이펙트) | STRONG |
| `[EMITTER]#standard` | 클립 루트 0프레임 | 파티클 이미터 | 31 | POSSIBLE |

`[ANIME]#`은 같은 파트 안의 kind 3 인스턴스와 별개다. 이걸 처리하지 않으면
682개 중 100개 이펙트에서 서브 애니메이션이 통째로 빠진다. 참조 대상 파트가
파일에 없는 경우도 352개 중 33개 있다(그건 그릴 수 없다).

### 루프 판정

파츠마다 길이가 다르므로(31~4800프레임) 전부 자기 길이로 되감으면, 끝 포즈가
시작 포즈와 다른 파츠가 화면을 가로지르다 제자리로 튄다. 675개 문서 검증에서
596개 이펙트·17,443개 파츠가 그랬다.

파츠의 68%는 끝 포즈가 시작 포즈로 돌아온다(닫힌 루프). 그것만 되감고 나머지는
끝에서 멈춘 뒤 문서 주기(가장 긴 애니메이션 길이)마다 다시 시작하면, 급격 이동이
15,832회 → 4,274회로 줄고 전부 멈추는 방식보다 움직임이 33% 더 남는다.
파일에 인스턴스 재생 파라미터(loopNum/infinity 등)는 없다 — kind 3 노드의
`+0x48~+0x5c`가 전수 동일하다. [신뢰도] POSSIBLE (작성 관행 기반 판정)

## 7. 그리기

1. 부모→자식으로 2×2 + 이동 누적. ROTX/ROTY는 정사영에서 축 축소(`cos`)로 근사
   한다. **이건 근사이고 원본은 3D 회전이다.** [신뢰도] 근사임을 명시 / WEAK
2. 셀 쿼드는 `-pivot × 셀크기`에 놓는다. pivot은 셀 중심 기준 정규화 값이고
   PVTX/PVTY가 더해진다. [근거] 40개 이펙트 × 5프레임에서 스테이지 내부 비율
   99.7%(−pivot) vs 94.9%(+pivot). [신뢰도] STRONG
3. 정점 색상은 4개 값이 두 행으로 들어간다(행 우선). [근거]
   `Animss6CellPart::updateQuad`가 값 블록 `+0x24,+0x2c,+0x34,+0x3c`를 정점
   슬롯 2,3,0,1에 2개씩 묶어 복사. 어느 행이 위인지는 미확인. [신뢰도] STRONG /
   행 순서 POSSIBLE
4. 정렬은 `sortPartPriorityNodePrio` — priority 오름차순, 같으면 파트 순서 유지.
   [신뢰도] CONFIRMED
5. 정점 색상은 상수가 아니라 **키프레임 트랙**이다. `blend 0`이면 색 1개,
   `blend 1`이면 코너 4개(전수 일치). 1181005 화살표는 이 트랙이 0프레임
   빨강/파랑 → 45 시안 → 180 반전 → 225 빨강으로 움직이고, 16개 인스턴스가
   `[ADVANCE]#15,30,…240` 위상으로 서로 다른 프레임을 읽어 링 왼쪽은 빨강
   (평균 RGB 107,10,23) 오른쪽은 파랑(8,84,122)이 된다. [신뢰도] CONFIRMED
6. 텍스처 790장 중 462장에 알파 채널이 없고, 그것을 쓰는 파츠의 97%
   (7,448/7,699)가 Add 블렌드다. 회색조 팔레트 PNG의 평균값은 1.6~39.6으로
   거의 검다 — 즉 **강도 맵**이고 검은 픽셀은 "불투명한 검정"이 아니라 강도 0이다.
   팔레트 양자화로 바닥이 9/255 정도 떠 있어서, Add 파츠 300~500개가 겹치면
   그 바닥이 사각형으로 누적된다. 휘도를 알파로 만들어 투명하게 처리한다.
   [신뢰도] 강도 맵 STRONG / 휘도=알파 변환은 표시 선택
7. 셀 파츠 중 Add 78.5%, Mix 21.5%이고 Multiply/Subtract는 카드 이펙트에 없다.
   [신뢰도] STRONG

## 10. `[LOOP]` — 반복은 파일이 직접 말한다

**[확인된 사실]** USERDATA 문자열 `[LOOP]` 은 애니메이션의 **root 노드 0프레임**에
하나 붙는다. USERDATA 트랙의 키는 전부 1개이므로 파트별 이벤트가 아니라
**애니메이션 단위 플래그**다.

| 항목 | 값 |
| --- | --- |
| 애니메이션 총수 | 13,902 |
| `[LOOP]` 있음 | 13,085 (94%) |
| 없음(1회 재생) | 817 (6%) |
| 영향받는 노드-트랙 | 4,230 |
| 일부만 반복하는 이펙트 | 144 / 682 |
| 파트 기준 | 반복 358,627 · 1회 7,825 (2.1%) |

**[문제]** 종전 평가기는 이 플래그를 읽지 않고 "그룹의 절반 이상이 포즈를 닫지
못하면 정지" 라는 휴리스틱으로 정했다. 1회 재생 애니메이션을 되감으면 그 파츠가
프레임 경계에서 순간이동한다.

**[처리]** `tools/patch_loop.py` 가 CHK 를 다시 걸어 `(노드이름, 애니길이)` 로
기존 JSON 에 `loop` 를 주입한다(682개 전부 성공). 평가기와 검증기는 플래그가

## 13. 아이콘 합성 — 무엇이 원본이고 무엇이 우리가 더한 것인가 (측정)

### 13.1 CS 카드 원본에는 빈 이름판이 들어 있다

**[확인된 사실]** `CS<id>.CHK` 안에는 PNG 가 **한 장뿐**이고 태그는 `PHOTO`,
크기 128x128 이다(`CL` 도 한 장, 512x1024). 즉 게임이 배포하는 카드 자산은
사진 하나이며, 배경은 런타임 합성이다.

**[확인된 사실]** 그 사진 하단에 **빈 이름판(파랑/검정 바)이 이미 그려져 있다.**
카드 24장 표본에서 폭 118px 이상 불투명한 행이 이어지는 구간의 **아래 끝이
y123~124 로 고정**이다(최소 123 / 중앙 123 / 최대 124). 위 끝은 선수 몸통과
붙어 71~102 로 흩어진다. 2015 · 2018 · 2021 · 2024 · 2026 전 연도에서 확인.
판에 **글자는 없다** — 이름은 게임이 그 위에 따로 얹는다.

**[해석]** 우리가 `.rp-name` 에 깔던
`linear-gradient(180deg,rgba(9,11,15,0),rgba(9,11,15,.92) 45%)` 은
**원본에 없는 배경**이었다. 진짜 판은 사진 안에 있다.

**[처리]** 그라디언트를 뺐다. 글자 띠는 판 안에 맞춘다 — 아래 여백 4/128=3%,
높이 27/128≈21%. 실측 아래 여백 1.9px(예상 2.0), 띠 14px(판 13.2px), 치우침 0.

**[주의]** `.row-photo .rp-name` 규칙이 **세 벌** 있어(543 / 804 / 1069행) 마지막
블록에서 `background` 선언을 지워도 804행 것이 그대로 먹었다. 두 곳 다 지워야
했다. §13.4 참조.

## 14. 상세 이펙트가 카드를 못 채우던 이유 (측정)

"아이콘은 배경 때문에 더 커 보인다"는 지적을 수치로 확인한 기록.

**[확인된 사실]** 아이콘(`_S`)은 카드 정사각형을 **97~99%** 채운다. 상세(`_L`)는
카드 틀(512x660 논리 = 420x541 px) 안을 **81~84%** 밖에 못 채웠고, 빈 곳이
**아래쪽에 몰려 있었다**. 카드 높이별 덮음(1182005, f40):

```
y  0~ 20   72%      y200~400  100%
y 20~ 40   86%      y420      91%
y 40~ 60   95%      y440      80%
y 60~200  100%      y460      64%
                    y480      49%
                    y500      14%
                    y520~541   0~1%
```

**[근거]** 카드 사각형을 k 배로 줄여 가며 덮음을 재면 두 이펙트가 같은 값을 낸다.

| k    | 1201005          | 1182005 |
| ---- | ---------------- | ------- |
| 1.00 | 81% (불투명 56%) | 84%     |
| 0.90 | 91% (불투명 66%) |         |
| 0.80 | 98% (불투명 77%) |         |
| 0.75 | 99% (불투명 83%) |         |

이펙트가 꽉 채우는 범위는 카드의 **0.78배**. 1/0.78 = **1.28**.

**[경쟁 가설 — REJECTED]** "숨겨진 배경 파트를 우리가 빠뜨린다."
1182005 에서 안 그려지는 큰 파트는 `bg` / `bg_1` / `bg_2` (252x508, scaleX 2.5)
뿐인데, 원본 CHK 의 HIDE 키가 **`raw=01000000` (=1, 숨김)** 이다. 같은 클립의
다른 노드는 전부 `00000000`(보임)이므로 읽기가 뒤집힌 것도 아니다. 게다가 이
셀들은 **가산인데 평균 휘도 3**(거의 검정)이라 켜도 덮음이 늘지 않는다.

**[경쟁 가설 — REJECTED]** "클립의 다른 애니메이션에 보이는 판이 있다."
`bg` 가 속한 클립7 은 애니메이션이 **1개**뿐이다(`anime_1`, 241프레임).
clip0 의 `ef_1182005_b1_07_anime_3..6` 노드들은 모두 `iclip=7 ianim=0` 을 가리킨다.

**[경쟁 가설 — REJECTED]** "인스턴스 중첩이 MAX_DEPTH=3 에서 잘린다."
깊이별 노드 수는 1182005 {0:85, 1:290, 2:56}, 1201005 {0:146, 1:1003, 2:376},
1101005 {0:126, 1:410, 2:152} — **깊이 3 이상이 0개**라 버려지는 노드가 없다.

**[경쟁 가설 — REJECTED]** "화면의 크기 슬라이더로 맞추면 된다."
슬라이더는 스테이지 컨테이너를 통째로 키워 **카드도 같이 커진다**
(카드 worldScale 0.820 -> 1.066). 비율이 그대로라 덮음이 개선되지 않는다.

**[처리]** `FX_CARD_FILL = 1.28` 을 이펙트 배율에만 곱하고 `cardArtScale` 에
역수를 넣어 **카드의 화면 크기를 그대로** 둔다. 캔버스 px 도 그대로 두려고
오버스캔을 같은 배수로 나눈다.

```ts
const FX_FILL_SCALE = FX_SCALE * FX_CARD_FILL;
fxCanvasFor(FX_FILL_SCALE, doc?.stageW, doc?.stageH, fxView / 100 / FX_CARD_FILL)
<AnssStage scale={FX_FILL_SCALE * (fxScale / 100)} cardArtScale={1 / FX_CARD_FILL} .../>
```

예전 시도(1.32)가 되돌려진 이유는 **카드를 줄여서** 선수 사진이 작아졌기
때문이다. 이번에는 카드가 변하지 않는다.

**[검증]** 카드 420x541 px 유지, 캔버스 885x1397 유지.

| 이펙트  | 덮음        | 불투명      | 하단 15%   |
| ------- | ----------- | ----------- | ---------- |
| 1201005 | 81% → **98~99%** | 56% → 77~79% | 16% → 92~97% |
| 1182005 | 84% → **97~99%** | 67% → 83~86% | 16% → 80~91% |

아이콘(97~99%)과 같은 수준이 됐다.

**[신뢰도]** STRONG — 이펙트 2개 x 3프레임 실측, 인게임 스크린샷 역산(1.32)과
방향·크기 모두 일치. 정확한 값은 실물 스크린샷 한 장으로 더 좁힐 수 있다.

### 15.1 고친 것 — 가산 알파를 휘도에서 max 채널로

**[문제]** 가산 셀 변환이 `알파 = 휘도`, `RGB x 255/휘도` 였다. 항등식
`rgb x (휘도/255) x (255/휘도) = rgb` 는 `rgb x 255/휘도 <= 255` 일 때만 성립하는데,
휘도는 가중 평균이라 **채도가 있으면 max 채널 > 휘도** 다. 그래서 유채색 픽셀
대부분에서 `Math.min(255, ...)` 클램프가 걸렸다.

(254,102,6) → 휘도 136.5 → R 을 474 로 키우려다 **255 에서 잘림** →
복원값 R = 255 x 136.5/255 = **136** (원본 254). **빨강 46% 손실**. G·B 는 정확.
즉 **가장 밝은 채널만 골라서 깎는** 변환이었다.

**[처리]** `알파 = max 채널`. 그러면 `rgb x 255/max <= 255` 라 클램프가 원리적으로
불가능하고, 복원이 모든 픽셀에서 정확하다. 검정은 max 0 → 알파 0 (판 안 생김).
**[측정]** R-B +72 → **+81**, 순백 11~13% → 11~14%. 정확해졌지만 주범은 아니었다.
**[신뢰도]** CONFIRMED (전 정의역 항등)

## 17. 1회성 파츠가 배경을 정지시키던 문제

**[확인된 사실]** 원본 `[LOOP]` 플래그가 없는(=1회성) 파츠는 자기 애니메이션 길이
`len` 의 마지막 프레임에서 **영원히 고정**됐다. 마스터 클럭은 감기지 않으므로,
움직이는 파츠 대부분이 1회성인 이펙트는 그 길이를 지나는 순간 배경 전체가
**정지 화면**이 된다.

**[측정]** 681개 전수에서 *움직이는* 파츠(트랙 키가 2개 이상) 기준

| 1회성 비율 | 이펙트 수 | |
|---|---|---|
| 50% 이상 (거의 완전 정지) | 20 | 3% |
| 15~50% (부분 정지) | 35 | 5% |
| 15% 미만 | 626 | 92% |

`216004` 는 f239 이후 픽셀이 **완전히 동일**했다 —
f241 `8442/33.1` · f300 `8337/32.6` · f600 `8442/33.1` · f1200 `8442/33.2`.
`141004`·`141005` 는 f73, `111013`~`111123` 계열(10개)은 f60,
즉 **2초 만에** 멈췄다.

**[해석]** 게임에서 카드 배경은 계속 재생된다. `[LOOP]` 없음은 "한 번 재생하고
끝"이 아니라 "한 번 재생하고 게임이 다시 트리거"다. 뷰어에는 그 트리거가 없다.

**[처리]** 1회성 파츠 전체가 **같은 순간에** 처음으로 돌아가는 공용 주기를 둔다.
주기 = 1회성 파츠 `len` 의 최댓값 = 1회성 내용이 모두 끝나는 지점.

```ts
const c = ((frame % plan.cycle) + plan.cycle) % plan.cycle;
lf = Math.min(F - 1, Math.max(0, c + phase));
```

**[회귀 위험 없음 — 근거]**
1. `loops[i] === true` 인 파츠는 코드 경로를 타지 않는다. 1회성 파츠가 하나도 없는
   **544개(80%)** 는 바이트 단위로 동일하다.
2. 첫 주기 안(`frame < cycle`)에서는 `frame % cycle === frame` 이라 계산이 종전과
   같다. 실측으로도 216004 의 f5·f60·f119·f239 값이 수정 전후 완전히 일치했다.
3. 수정 후 216004 는 f1085 ≡ f5, f1140 ≡ f60, f1200 ≡ f119 로 되살아났고,
   141004·111073 은 f1400 까지 계속 변한다(표준편차 2.38 / 1.82).
4. 목록 아이콘 아틀라스 지표 불변: 발광 48,429 · 흰색포화 5.0% · 채도 0.520.

**[반박된 대안]** 1회성을 그냥 `loop` 로 바꾸기 — 열린 애니메이션이 자기 길이마다
제각각 튀어 "파츠가 따로따로 재생"되는 예전 증상(r23/r25)이 돌아온다. 공용 주기로
한 순간에 모으면 원본이 다시 트리거된 것처럼 읽힌다.

**[남은 것]** 주기 경계에서 한 번 튀는 것은 설계상 남는다(원본 재트리거와 동일).
`141004` 는 2.4초마다, `216004` 는 36초마다 한 번이다.

**[신뢰도]** 정지 현상 CONFIRMED(픽셀 실측) · 재시작 주기 선택 STRONG

## 21. 목록 행에서 선수 사진만 비던 문제 (lazy 우선순위 역전)

**[증상]** 목록에서 일부 행이 **배경 이펙트와 이름 띠만** 보이고 선수 사진이
비어 있다. 배경 원본이 그대로 드러나 보인다.

**[확인된 사실]** 한 행에는 이미지가 세 겹이다.
| 겹 | 자산 | 크기 | 로딩 |
|---|---|---|---|
| 뒤 | 이펙트 캔버스 | — | 즉시(공유 렌더러) |
| 가운데 | 선수 사진 CS | 20~30KB | **lazy** |
| 아래 | 이름 띠 CL 아틀라스 | **131KB** | eager |

가장 작고 가장 중요한 선수 사진만 lazy 였다. 무겁고 부차적인 아틀라스가 먼저
오고, 배경은 항상 즉시 그려지므로, lazy 가 늦거나 실패하는 구간에서
"배경만 노출" 상태가 그대로 보인다.

**[측정]** 뷰포트가 0인 환경(교차 관찰자가 영영 발화하지 않음)에서
선수 사진 **0/25**, 이름 띠 25/25. `loading="eager"` + `fetchPriority="high"`
로 바꾼 뒤 선수 사진 **25/25**.

**[근거]** 목록은 한 번에 25행만 그린다. CS 25장 = 600KB 남짓으로, 이미 eager 인
이름 띠(25 x 131KB = 3.3MB)보다 훨씬 가볍다. lazy 로 아낄 것이 없다.

**[처리]** `app/page.tsx` `RowIcon` 의 `.rp-art` 를 eager + 높은 우선순위로.

**[신뢰도]** CONFIRMED (0/25 → 25/25 실측)

아이콘은 76 CSS px 로 표시되어 dpr 2 화면에서 152 물리 화소인데 타일 백킹이

제거 전후 계산값이 완전히 같음을 확인했다 — 박스 37x10, 이미지 86x172,

**확인했으나 문제 아니었던 것.** `prepare()` 의 `yieldSoon` 은 rAF 가 아니라

## 25. 셀 → 시트 매핑이 뒤바뀌어 그림이 빠지고 있었다

## 27. UV 스케일 0 이 만든 "떠다니는 네모"

**[증상]** 화면에 단색 네모가 떠다닌다.

**[원인]** 렌더러는 `sample(t.uvsx, lf, 1) || 1` 로 **보간 결과**가 정확히 0 일
때만 1 로 바꿨다. 그래서 1.0 -> 0.0 으로 내려가는 트랙은 0.5, 0.2, 0.05 … 를
지나며 UV 샘플 창이 한 점으로 오그라들고, 쿼드 전체가 **텍셀 몇 개를 늘린 단색
사각형**이 된다. 그러다 정확히 0 에서만 갑자기 원래 크기로 되돌아온다.

**[실측]** `1001004` 의 `wa_shibuki_1` — 트랙 `[0,1] [25,1] [50,0]`

| 프레임 | 40 | 45 | 48 | 49 | 50 |
|---|---|---|---|---|---|
| 수정 전 창 폭 | 0.40 | 0.20 | **0.08** | **0.04** | 1.00 (급격 복귀) |
| 수정 후 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |

**[범위]** 전체 `uvsx/uvsy` 키 82,808개 중 값이 0 인 것 **24,021개(29%)**.
그중 그 프레임에 **알파가 살아 있는 것이 4,033개**(숨겨진 것 610개) — 대부분
화면에 보이는 상태로 0 을 지난다.

**[아직 모르는 것]** 이 속성이 절대 배율인지 1 기준 증분인지는 데이터로 못
가린다 — 트랙 첫 키가 0.0 인 것 38% · 1.0 인 것 38% 로 정확히 갈린다. 다만
- `uvsx = -1` 정적 트랙 346개는 **절대(좌우 반전)** 로 읽어야 말이 되고,
- 0 은 어느 쪽으로 읽어도 "변화 없음" 이어야 한다.

**[처리]** 값의 의미는 절대로 두고, **0 인 키만 1 로 바꾼 뒤 보간**한다
(`planOf` 에서 문서당 한 번). 0 이 아닌 값의 의미는 하나도 바뀌지 않고 붕괴
구간만 사라진다. 검증: `1001004` 프레임 20~80 에서 창 폭 2% 미만인 메시
**0 / 45~49개**.

**[신뢰도]** 붕괴가 사각형을 만든다 = CONFIRMED (기하 + 실측) ·
0 의 정확한 의미 = POSSIBLE

```
eff_t  kind=1 blend=2(Add)  cell=fan01_01_t (2,2) 256x64
       v = blend 1, corners  [255,255,255,0.0] [255,255,255,0.0]
                             [255,255,255,1.0] [255,255,255,1.0]
       트랙 = hide, uvy(-0.25 -> 0.85) 뿐

eff_u  cell=fan01_01_u (2,66) 256x64
       v = blend 1, corners  [1.0] [1.0] [0.0] [0.0]   (t 의 반대)
```

즉 두 파츠는 같은 그림(`fan01_01` 256x424)의 **위아래로 붙은 64px 조각**이고,
정점색의 **RGB 는 네 모서리 모두 흰색이며 알파만 0↔1** 이다. 이 알파 램프가
띠의 바깥쪽 끝을 지워 부드러운 광선을 만든다.

**[문제]** 렌더러는 정점색의 알파를 두 경로 모두에서 버렸다.
1. 스프라이트 경로 `cellTexture` 의 2x2 램프가 `rgb(...)` 만 칠하고 `c[3]` 을
   무시했다. 캐시 키도 `slice(0,3)` 이라 RGB 가 같고 알파만 다른 그라데이션이
   같은 항목으로 뭉개졌다.
2. UV 파츠는 시트를 그대로 샘플하는 Mesh 라 그 경로 자체를 타지 않는다.
   PIXI v8 Mesh 는 정점색을 지원하지 않는다(배처에만 `aColor` 가 있다).

그래서 부드럽게 사라져야 할 띠가 **각진 불투명 판**이 됐다.

**[측정]** 정점색 키 380,400개 중 모서리별 알파가 서로 다른 것 **4,584개**,
영향 이펙트 **48개**. 그중 **3,970개는 RGB 가 네 모서리 모두 같아 알파만이
유일한 효과**다. 경로별로는 UV(메시) **2,989 / 37개 이펙트**, 일반(스프라이트)
**1,595 / 42개 이펙트**.

**[처리]**
- 스프라이트: 2x2 알파 램프를 `destination-in` 으로 한 번 더 곱한다. 캐시 키에
  알파를 넣는다. 최종 알파 = 셀알파 x 모서리알파.
- 메시: PIXI high-shader 에 `vColor *= aColor` 한 줄짜리 bit 를 끼운 커스텀
  셰이더를 만들고, 지오메트리에 `aColor`(float32x4 x4정점) 를 추가한다.
  템플릿이 `finalColor = outColor * vColor` 이므로 정점 알파가 그대로 곱해진다.
  그라데이션이 있는 메시에만 붙인다.

**[검증]** `1285005` 프레임 40 — 메시 212개 전부 정점 알파가 실려 있고
(`aColor` 의 모서리 알파가 서로 다름), 콘솔 오류 0건. 화면에서 각진 날개가
사라지고 부드러운 광륜이 된다.

**[신뢰도]** 원인 CONFIRMED (원본 정점색 값) · 모서리↔정점 대응은 스프라이트
경로와 같은 규약 (POSSIBLE — 뒤집히면 그라데이션 방향만 반대)

## 29. 원본 CHK 바이트 커버리지 — 안 읽은 데이터는 없다

"원본에서 못 찾은 게 있는 것 같다"는 의심에 답하기 위해, 파서가 **읽지 않는 모든
바이트 범위**를 전수로 훑어 값이 변하는지 확인했다(`_L` 120개 표본).

| 레코드 | 안 읽는 오프셋 | 결과 |
|---|---|---|
| texture (0x78) | 0x08 0x0c 0x58 0x5c 0x60 0x64 0x74 | 전부 **상수**(0 또는 1) |
| cell (0x60) | 0x58 0x5c | 전부 **상수** 0 |
| clip (0x80) | 0x44 0x48 0x4c 0x58 0x5c | 전부 **상수** (0x44 는 항상 11) |
| node (0x68) | 0x50 0x54 0x58 0x5c | 전부 **상수** (0x50 항상 1) |
| anim (0x78) | 0x40 0x44 0x50 0x54 | 전부 **상수** |
| anim (0x78) | 0x60 0x64 | 2,882개 중 **14개만** 비영 — 노이즈 수준 |

**[해독된 미지 필드 2개]**
- **keyframe +0x18** — 익스포터 주석이 `interp` 라 적어 둔 자리인데, 실제로는
  **값의 종류 태그**다: float=2 · CELL=3 · 플래그(FLIPH/HIDE/IMGFLIPH)=1 ·
  VERTEXCOLOR=4 · USERDATA=5 · PRIORITY=0. 보간 곡선은 `+0x04` 가 맞다
  (값 분포 1=Linear 350,408 · 0=Hold 102,309 · 3=Bezier 24,659 · 5=Decel 12).
- **node +0x4c** — 0/1 플래그. 값이 1 인 5,133개가 **전부 이름 `root` · kind 0**
  이다. 즉 루트 노드 표식이며 재생과 무관하다.

**[결론]** 원본 파일에서 **읽지 않고 남은 정보는 없다**. 남은 차이는 데이터가
아니라 **해석**에 있다. 특히 아직 확정 못 한 것은 두 가지다.
1. 인스턴스가 부모 시계로 도는지 독립 시계로 도는지 — 인스턴스 파라미터
   (attr 31)가 전수 2키뿐이라 파일이 답을 갖고 있지 않다.
2. `[LOOP]` USERDATA 문자열을 엔진이 실제로 읽는지 — 문자열이라 확증 불가.

이 둘은 **게임 실캡처** 없이는 판정할 수 없다.

## 30. 속성 20·21 = SIZE_X / SIZE_Y — 파싱조차 하지 않고 있었다

[확인된 사실]
- 트랙 속성 id **20·21** 은 코퍼스에 148개 키(20이 75개, 21이 73개)로
  존재하는데 `tools/export_anim.py` 의 `WANT` 에 없어서 **JSON 으로 나가지도**
  **않았다.** 즉 evaluate 의 버그가 아니라 추출 단계의 누락이었다.
- 20·21 은 **항상 같은 노드에 쌍으로** 나타난다. 키프레임의 값 종류 태그
  (`+0x18`)는 2(float)다.
- 셀을 가진 파츠에서 값의 범위는 **75.7872 ~ 547.4722** (326키). 전부
  픽셀 크기다. 예: `bowa_wakka_orange` 는 셀이 128x128 인데 20=145.9232,
  21=138.8625 → 실제 표시 크기는 셀보다 **14% 크다**. `chiri1` 은 같은
  128 셀에 20=75.7872 → **41% 작다**.
- 속성 순서상 17 PIVOTY 와 22 IMGFLIPH 사이의 빈칸이며, SpriteStudio 계열의
  속성 배열(PIVOT → SIZE → IMGFLIP)과 자리가 맞는다.

[해석] 20·21 은 셀 크기를 무시하고 **표시 크기를 픽셀로 직접 지정**한다.
따라서 배율은 `k = SIZE / 셀크기` 이고, 이는 SCALE(7·8)과 곱해진다.

[구현] `evaluate.ts` 에서 로컬 배율에 접어 넣었다. 쿼드 계산식 자체는
건드리지 않으므로 SIZE 가 없는 이펙트는 `k=1` 이 되어 **결과가 비트 단위로
동일**하다.

```ts
const kx = t.szx && cell.w ? sample(t.szx, lf, cell.w) / cell.w : 1;
const ky = t.szy && cell.h ? sample(t.szy, lf, cell.h) / cell.h : 1;
dr.a = w.a * kx; dr.b = w.b * kx; dr.c = w.c * ky; dr.d = w.d * ky;
dr.x = w.x + dr.a * ox + dr.c * oy;
dr.y = w.y + dr.b * ox + dr.d * oy;
```

[근거 — A/B 실측] 영향 24개 이펙트를 f=0/30/60/100/130/200 에서 SIZE 있음 /
SIZE 트랙 제거 두 벌로 평가해 비교했다.
- 바뀐 드로우 **620 / 23,532**
- 바뀐 이펙트 **12 / 24**
- 배율 변화 폭 **0.592x ~ 1.600x**
- SIZE 를 가진 파츠 중 배율이 1 인(무의미한) 것은 4개뿐 — 나머지 159개는
  실제로 크기가 틀리게 그려지고 있었다.
즉 이 파츠들은 최대 **60% 크게 / 41% 작게** 그려지고 있었다. 사용자가 말한
"가공되어 있지 않은 네모가 날아다닌다" 와 방향이 일치한다.

[경쟁 가설 — 셀 없는 파츠의 SIZE] 코퍼스 전체에서 셀이 없는 파츠에 붙은
20·21 은 **6개 키뿐**이고, 전부 한 노드
(`b3_b6___housya_sets_all_3`, 자식 6개, 1015004·1015005)이며 값이 전부
**0.8** 이다. 픽셀 크기라면 0.8px 은 말이 안 되므로 두 갈래다.
1. 인스턴스/그룹에 대해서는 **배수**로 동작한다 (하위 전체 0.8배).
2. 셀이 없으면 SIZE 의 기준이 없으므로 엔진에서도 **무시**된다 (편집기 잔여값).
근거가 6개 키·1개 노드뿐이라 어느 쪽도 확정할 수 없다. 현재 구현은
`cell.w` 로 가드하므로 **2번(무시)** 으로 동작한다.
[신뢰도] 셀 있는 파츠 = CONFIRMED · 셀 없는 파츠 = 미결(POSSIBLE)

[재추출] 영향 이펙트 25개를 다시 뽑아 `anim-gz` 24개 / `anim-s-gz` 25개를
교체했다. 참조 스프라이트 1,302개 전부 이미 있어 새로 만들 것은 없었다.
`1114005` 는 이전과 동일하게 현재 추출기로 파츠가 0개라 실패하며, 기존
파일을 그대로 두었다(별개 미해결 건).

[아직 모르는 것] SIZE 와 IMGFLIP(22·23)이 같이 걸린 파츠에서 부호 처리가
맞는지는 해당 조합이 코퍼스에 없어 검증하지 못했다.

[다음 검증] 인스턴스 루트의 0.8 을 배수로 해석한 화면과 무시한 화면을
1015004 에서 나란히 놓고 원본 게임 캡처와 대조.

## 31. 메시 정점 알파를 프리멀티플라이하지 않아 그라데이션이 무시됐다

[증상] 사용자가 `ANSS_EF_1285005_L.CHK` 의 `eff_t` · `eff_u` 를 지목했다.
"네모난 게 떠다닌다". 실제로 그 두 레이어만 남기고 렌더하면 **모서리까지 꽉 찬
사각 블록**이 링을 그리며 돈다.

[확인된 사실 — 원본 구조]
- `eff_t` / `eff_u` 는 **항상 한 쌍**이다. 같은 부모에 붙고 자기 변환 트랙이
  하나도 없다. 가진 것은 CELL(0) · HIDE(13) · VERTEXCOLOR(14) · UVTY(25) 뿐.
- 두 셀은 아틀라스에서 **세로로 맞붙은 두 슬라이스**다.
  `fan01_01_t`(2,2,256,64) 와 `fan01_01_u`(2,**66**,256,64) — 둘 다
  `fan01_01`(2,2,256,**424**) 이라는 긴 곡선 꼬리 텍스처의 윗부분이다.
- 피벗이 `py=-0.5` / `py=+0.5` 로 서로 반 칸씩 어긋나 **위아래로 이어 붙는다**.
  실제 드로우에서 `eff_u` 는 `eff_t` 로부터 로컬 y 로 정확히 -64 만큼 떨어진다.
- 정점 색 알파가 **서로 정반대**다 — `eff_t` = `[0,0,1,1]`, `eff_u` = `[1,1,0,0]`.
- `uvy` 가 -0.25 → 0.85 로 흐른다(60프레임).
[해석] 128픽셀짜리 창이 424픽셀 꼬리 텍스처를 따라 내려가고, 창의 양 끝이
정점 알파로 부드럽게 꺼진다. 즉 **끝이 사라지는 흐르는 띠**가 의도다.

[원인] 렌더러는 `aColor` 를 `(1, 1, 1, a)` 로 넣고 있었다. PIXI 의 `vColor` 는
**프리멀티플라이드**다. 가산 블렌드는 원본 RGB 를 그대로 더하므로(ONE, ONE)
알파 채널만 낮춰 봐야 **화면이 전혀 어두워지지 않는다.** 그래서 그라데이션이
통째로 무시되고 사각형의 하드 엣지가 그대로 드러났다.

[근거 — 동일 프레임 A/B] 1285005 에서 `eff_t`·`eff_u` 만 남기고 f30 을 렌더:

| | 켜진 픽셀 | 평균 밝기 |
|---|---|---|
| `rgb=1` (종전) | 225,158 | 107 |
| `rgb=a` (수정) | 225,158 | **52.7** |

켜진 픽셀 수가 **완전히 같다** — 알파 채널은 원래 맞게 들어가고 있었고 RGB 만
안 줄고 있었다는 뜻이다. 이펙트 전체(f45)로 보면 흰색 포화가
**4.71% → 3.58%** 로 내려가고 불링의 결이 살아난다.

[처리]
```ts
cd[o] = a; cd[o + 1] = a; cd[o + 2] = a; cd[o + 3] = a;
```
모서리 알파가 없는 메시는 `a = 1` 이라 **결과가 종전과 동일**하다.

[범위] 메시 경로(UV 또는 정점변형) + 모서리 알파를 가진 파츠 **2,631개 /
이펙트 40개**. 그중 가산 1,772 · 그 외 859. 가산에서는 효과가 **전무**했고
일반 블렌드에서는 프리멀티플라이드 규약을 깨 알파 0 모서리까지 색이 더해지고
있었다(둘 다 이번에 고쳐진다).

[영향 없음] 스프라이트 경로는 캔버스 `destination-in` 으로 알파를 텍스처에
구워 넣고 PIXI 가 업로드 시 프리멀티플라이하므로 원래 맞았다. 아이콘 아틀라스
(`thumb.ts`)는 메시를 쓰지 않아 무관하다. 모서리 알파 메시 셀 2,550개가 전부
시트 참조를 갖고 있어 "구운 텍스처 + aColor 이중 적용" 경로는 발생하지 않는다.

[기각한 가설] 텍스처 레코드 `+0x58` 의 0/1 플래그를 UV wrap 모드로 의심했다.
코퍼스에서 42개 텍스처만 1이고, UV 트랙을 가진 노드 8,412개 중 그 플래그가
1인 것은 154개뿐이며 반대로 flag=1 인데 UV 가 없는 것도 106개다. **상관 없음 —
REJECTED.**

[부수] `window.__anss.byPart` 를 추가했다. 파츠 이름 -> 이번 프레임에 그려진
스프라이트 목록이라, 특정 레이어만 남기고 렌더해 원본과 대조할 수 있다.
이번 진단이 그것으로 가능했다.

## 32. 베지어 시간 핸들을 정규화하지 않아 이징이 통째로 무의미했다

[증상] 사용자: "재생되면서 움직이는 게 아니라 그냥 움직이긴 해."
파츠가 **등속으로 미끄러지거나 툭툭 끊겨서** 애니메이션이 연출로 읽히지 않는다.

[확인된 사실 — 핸들의 단위]
키프레임 `+0x08` 의 float 4개는 `[바깥핸들Δ프레임, 바깥핸들Δ값,
다음키 안쪽핸들Δ프레임(음수), 그 Δ값]` 이다. 시간 성분은 **프레임 단위**다.

| | 값 |
|---|---|
| 핸들 실린 구간 | 74,238 (표본 200개 문서) |
| `h[0]` 중앙 / `h[2]` 중앙 | 4.0 / −6.0 |
| 구간 길이 중앙 | 20 |
| **0..1 좌표로 불가능(`h[0]>1` 또는 `h[2]<−1`)** | **97.2%** |
| `h[0]/span`, `h[2]/span` 최빈 | (0.2,−0.2) (0.1,−0.1) (0.3,−0.3) |

값 성분은 오프셋이 맞다 — `|h[1]|/|Δ값|` 중앙 0.023, 1을 넘는 건 1.1%뿐이다.
(초당율 가설이면 40.2%가 1을 넘어 과도 오버슈트가 된다 → 기각.)

[원인] `bezierU(t, h[0], h[2])` 로 **프레임 값을 그대로** 0..1 좌표에 넣고 있었다.
예: `span=50, h=[4,0,-4,0]` → `x0=4, x1=-4`. 그러면 `x(u)` 가 `u=0.2` 에서 이미
1.16 이 되어 **단조가 아니고**, 뉴턴 반복의 해가 의미를 잃는다.

[근거 — 전 구간 수치] 옛 공식과 새 공식을 코퍼스 전 베지어 구간에서 직접 비교:

| | 값 |

## 34. 스크롤 창(_t/_u) — UV 이동 단위는 창이 아니라 **원본 이미지**다

[증상] 사용자가 `ANSS_EF_1285005_L` 의 `eff_t`·`eff_u` 를 여러 번 지목했다.
"전혀 개선이 안 되고 **움직이기만** 함", "이미지를 움직인다고 완성되는 이펙트가
아니라 이미지를 가지고 새롭게 뭘 해야 되는 거잖아", "너가 활용을 못하는 게 있다".

[확인된 사실 — 기하]
`eff_t`·`eff_u` 는 자기 변환 트랙이 하나도 없고 **UV 세로 이동 하나로만**
애니메이션한다. 그 셀은 같은 시트의 **더 큰 셀에서 잘라낸 얇은 창**이다.

| 창 | 시트 rect | 원본 |
|---|---|---|
| `fan01_01_t` | (2, **2**, 256, 64) | `fan01_01` (2, 2, 256, **424**) |
| `fan01_01_u` | (2, **66**, 256, 64) | 〃 |
| `brush01_t/_u` (1151003) | 156x64 x2 | `brush01` 156x**256** |
| `wa_t` (1142004) | 124x128 | `wa_long` 124x**252** |

[원인] UV 이동 1.0 을 **창 높이(64)** 로 잡고 있었다. 그래서 창이 시트
-3~120행만 훑고 멈췄다 — 원본 424행의 **29%** 다.

[근거]
1. 우리가 보여 주던 구간(2~120행)의 평균 알파는 **31.1**, 한 번도 안 보여 준
   구간(120~300행)은 **65.7** 이다. 리본에서 가장 밝은 부분이 통째로 빠졌다.
2. 원본 트랙은 `uvy: -0.25 → 0.85` 에서 멈춘다. 단위를 원본 높이(424)로 두면
   0.85 가 **정확히 426행 = 리본의 끝**에 닿는다. 창 높이로 두면 120행에서
   멈추는데 왜 거기서 멈추는지 설명할 수 없다.
3. 121프레임 주기 중 60~120프레임이 `uvy = 0.85` 로 정지한다. 원본 단위로 읽으면
   그 구간에서 창이 이미 그림 밖(빈 영역)이라 **정지가 보이지 않는다.**
   창 단위로 읽으면 그림 한가운데서 절반의 주기 동안 얼어붙는다 —
   그게 "움직이기만 한다"의 정체다.

[처리 — 서명으로 좁혔다] 단순 포함 관계로 잡으면 UV 셀 참조의 78%(23,392개)가
걸리는데 대부분 아틀라스에서 우연히 겹친 것이다(`hahen_01 ⊂ dot_1`). 그래서
**스크롤 창 서명**만 채택한다:
- 같은 텍스처 안에서 x·폭·크기가 같은 형제 창이 **바로 위/아래에 붙어 있고**
- 그 둘을 감싸는 **높이 2배 이상**의 셀이 있을 것

→ **4,008개 파츠 / 110개 이펙트**. 서명에 맞지 않으면 `uh` 가 붙지 않고
`uvUnitY === rh` 라 결과가 종전과 **완전히 동일**하다.

- `export_anim.py`: 셀에 `uy`(원본 상단) · `uh`(원본 높이)를 기록
- `AnssStage.tsx`: `const uvUnitY = c.uh ? c.uh / c.sh : rh` 로 세로 이동만 분리
- `types.ts`: `uy` · `uh`

[검증] 1285005 `eff_t` 가 훑는 시트 행:

| | 종전 | 지금 |
|---|---|---|
| f0 → f30 → f60 | 4~68 → 39~103 → 56~120 | **13~77 → 246~310 → 362~426** |
| 원본 424행 사용률 | 29% | **100%** |

**[정정] 화면 형태는 거의 바뀌지 않는다.** 같은 세션에서 토글
(`window.__anss.noScrollWindow`)로 A/B 를 재면 f0~f60 의 실루엣은 전후가 같은
쐐기 무리이고, 달라지는 것은 **밝기 감쇠**뿐이다.

| 프레임 | f0 | f12 | f24 | f36 | f48 | f60 |
|---|---|---|---|---|---|---|
| 창=64행 (종전) | 57.8 | 37.3 | 30.9 | 34.4 | 40.1 | 42.2 |
| 창=원본 424행 | 57.7 | 35.7 | 26.0 | **14.4** | **15.5** | **7.4** |

이는 위 [근거] 3 과 일관된다 — 창이 그림 밖으로 나가므로 뒤로 갈수록 사라진다.

[적용 안 됨] `1201005` 는 이 서명에 맞는 셀이 0개라 이번 변경과 무관하다.

[신뢰도] 기하 서명 CONFIRMED · "원본 높이가 UV 단위" 해석은 STRONG

## 35. 목록 아이콘 렌더러에 UV 경로가 아예 없었다

[증상] §31·§32·§34 를 연달아 고쳤는데 사용자가 "하나도 변한 게 없음" 이라고 했다.

[원인] 화면이 둘이다.
- `AnssStage.tsx` — 상세/이펙트 페이지. 메시 경로가 있어 UV 를 그린다.
- **`thumb.ts` — 선수 목록 아이콘.** 모든 파츠를 `new Sprite(cellTexture(...))`

  움직이기만 한다.

즉 아이콘을 보고 있었다면 §31(정점 알파) · §34(스크롤 창) 은 물론 UV 자체가
한 번도 반영된 적이 없다. `evaluate` 안에서 끝나는 §30(SIZE) · §32(베지어)만
닿았다.

[측정] 아이콘 문서(`anim-s-gz`)의 셀파츠 **7,274개 중 494개(6.8%)** 가 UV
트랙을 갖고, **663개 아이콘 중 161개**가 영향을 받는다. 스크롤 창(uh)은 23개,
정점변형(xt)은 2개다.

[처리] `AnssStage` 의 메시 규약을 그대로 가져왔다 — 시트를 텍스처로 삼고 UV 창을
직접 넣으며, 정점 알파는 프리멀티플라이드(§31), 스크롤 창은 원본 높이를 이동

`AnssStage` 에서 내보내 두 화면이 같은 코드를 쓰게 했다. UV 가 없는 파츠는
종전대로 Sprite 라 결과가 같다.

(`AnssStage` 는 재사용한다). 동작은 같고 비용만 다르다.

## 37. 세로 피벗 부호가 반대였다 — `_t`(top) / `_u`(under)

[증상] 사용자: "이상한 곳에서 이미지가 나오고 이동한다", "t/u 이거 탑 언더였노".

[확인된 사실] 파츠 이름의 `_t` · `_u` 는 **top / under** 다. 한 쌍은 위아래로
붙어 하나의 띠를 이룬다. 셀도 그렇게 잘려 있다 —
`fan01_01_t`(시트 2~66행) 위, `fan01_01_u`(66~130행) 아래.

[원인] `evaluate` 가 `oy = -pvy * cell.h` 로 계산해 **위아래가 뒤집혔다.**
1285005 의 세 쌍을 재면 `eff_u` 가 `eff_t` 로부터 로컬 y **-66.6** — 즉
under 조각이 top 조각 **위**에 놓인다. 띠가 이음매에서 끊기고, 피벗이 0 이
아닌 모든 파츠가 제 위치에서 **피벗의 2배**만큼 어긋난다.

[근거 — 코퍼스 전수]

| | `-pvy` (종전) | `+pvy` |
|---|---|---|
| `_t`/`_u` 쌍이 **이미지 순서대로** 놓임 | **0 / 398** | **362 / 398** |
| 셀이 스테이지 박스 안에 들어오는 비율 | 99.37% | 98.88% |

종전 부호를 정당화한 것은 아래쪽 통계뿐이었는데 차이가 **0.5%p** 라 부호를
가릴 근거가 못 된다. 위쪽은 **0 대 362** 로 갈린다.

[처리] `const oy = pivotYSign * pvy * cell.h;` (기본 `+1`).
`window.__anssPivotY = -1` 로 종전 동작과 즉시 비교할 수 있다.

[신뢰도] CONFIRMED — 이름 규약(top/under)이라는 의미 근거와 398쌍 전수 측정이
같은 방향을 가리킨다.

[남는 36쌍] `+1` 에서도 순서가 안 맞는 쌍이 36개 있다. 세로로 쌓이지 않은
(가로로 나란한) 쌍으로 보이며 별도 확인이 필요하다.

### 37.1 [철회] 위 판정은 틀렸다

사용자가 r50 을 보고 "이상한데 뭔 짓을 한 거임" 이라고 했고, 맞다.

[내가 틀린 이유] 부호를 재는 좌표계를 잘못 맞췄다.
- `evaluate` 의 world 는 **y-up** 이고, `AnssStage` 가 `-dr.b · -dr.c · -dr.y`
  로 **뒤집어서** PIXI 에 넘긴다.
- 반면 메시 정점 배열은 `-hh` 가 이미지 **위**(v0)다.
- 즉 두 규약의 y 방향이 반대다. 그런데 나는 `(d.c, d.d)` 로 **evaluate 좌표**에
  투영해 놓고 **메시 규약**("+y = 이미지 아래")으로 해석했다. 그래서
  "0/398 vs 362/398" 이 통째로 뒤집힌 값이었다.

[처리] `pivotYSign` 을 `-1` 로 되돌렸다(r51). 종전 근거인 "셀이 스테이지 안에
들어오는 비율 99.37% vs 98.88%" 가 여전히 `-` 를 지지한다.

[교훈] 부호를 검증할 때는 **최종 스크린 좌표**에서 재야 한다. evaluate 중간
좌표에서 잰 값은 렌더러의 y-flip 때문에 결론이 반대로 나온다.

## 44. Vcol 의 ARGB 최상위 바이트가 **코너 알파**다 — 통째로 버려지고 있었다

[증상] 사용자가 682개를 전수 검토해 라벨을 매겼다(엉망 23 · 살짝 128).

[확인된 사실] `AnimssValue::Vcol` 의 코너 항목은 `ARGB(u32) + rate(f32)` 인데,
종전 `read_vcol` 은 **A 바이트를 버리고** rate 만 알파로 썼다.

[결정적 근거 — 951004 `ef_951000_07_02b_2` vcol 9키 원시 덤프]
| 프레임 | 코너 ARGB | 뜻 |
|---|---|---|
| f0 | `0x001d5ce8` x4 | A=00 — 완전 투명 |
| f5 | 위 2코너 `0xff…` · 아래 2코너 `0x00…` | **수직 와이프 그라데이션** |
| f32~f140 | `0xff1d5ce8` x4 | 완전 표시 |
| f148~f165 | 다시 A=00 코너 | 페이드아웃 |

rate 는 전 구간 1.0 — envelope 이 전적으로 A 바이트에 있다. 색 #1d5ce8 은
화면에 항상 떠 있던 "파란 판"과 정확히 일치한다. 종전 파서는 이 9키를
전부 `alpha 1.0` 으로 만들어 **잠깐 스쳐야 할 붓자국이 상시 점등**됐다.

[전수 측정]
- vcol 키 91,999개 중 **A<255 = 22,543개 (24.5%)**
- 영향 이펙트 **471 / 682**
- 사용자 라벨과 교집합: **엉망 23개 중 22개 · 살짝 128개 중 127개**

[합성 규칙] 유효 코너 알파 = `rate x (A/255)`.
- eff_t 류(§31)는 rate 에 0/1 그라데이션, A=ff → 종전과 동일.
- 이 케이스는 rate=1, A 가 envelope → 이제 반영.
둘 다 곱으로 성립한다.

[검증] 951004: 상시 점등 파란 판 -> f5 거의 투명, 서서히 등장, f150 페이드.

[부수 — r60 캐시 회귀] 캐시 상한이 밀려난 텍스처를 destroy(true) 해서 화면
스프라이트의 source 가 null 이 되는 크래시("alphaMode of null", 사용자 보고).
참조만 내려놓도록 고침 — GPU 해제는 PIXI TextureGCSystem 에 맡긴다.

## 45. 이동 좌표는 로컬 픽셀이고 부모 행렬이 곱해진다 — 1285005 좌표계 가설 기각

[확인된 사실] `AnimssPart::updateWorldMatrix()`는 로컬 행렬을
`scale → rotateZYX → trans` 순서로 만들고, 부모가 있으면 네이티브의 행렬 곱
연산자로 `parentWorld × local`을 계산한다. 로컬 이동값은 별도의 캔버스/스테이지
비율로 재조정하지 않는다.

[근거 — 원본 네이티브] `libAll.so`의
`AnimssPart::updateWorldMatrix()`(`0x3e88844`, 0x184바이트) 디스어셈블:
- 파트 `+0x50/+0x54`를 `Matrix3D4x4::scale`에 전달
- `+0x44/+0x48/+0x4c`를 `rotateZYX`에 전달
- `+0x38/+0x3c/+0x40`을 `trans`에 전달
- 부모 `+0xcc` 행렬과 로컬 행렬을 `Matrix3D4x4::operator*`로 곱해 세계행렬 저장

[근거 — 데이터 전수] 사용자 판정 `clean` 612개와 `minor` 70개의 위치 트랙을
캔버스 크기로 정규화해 문서별 최대 이동을 비교했다.

| 판정 | 캔버스를 넘는 위치 트랙 | 최대 이동비 p50 | p90 | p95 |
|---|---:|---:|---:|---:|
| clean 612개 | 1,403 | 0.69 | 1.22 | 1.44 |
| minor 70개 | 266 | 0.57 | 1.29 | 1.41 |

`1285005 fan02_03/set`의 y `0→323`은 320×320 하위 클립을 빠져나가는 로컬
이동이다. 상위 인스턴스의 y=114~178·회전·scale 0.5~1.3과 합성된다. 특히 첫
사본의 부모 y-scale은 0.8이라 현행 부모 합성은 이동을 323→약 258로 **줄이는**
방향이다. 부모 배율을 빼거나 720×1484 저작 스테이지 비율을 적용하면 원본
네이티브와 달라진다.

[경쟁 가설]
- `323/320`이므로 이동을 저작 스테이지 비율로 축소해야 한다: **REJECTED**.
  정상군에도 같은 크기의 캔버스 이탈 이동이 더 흔하고 네이티브에 재조정이 없다.
- 부모 scale이 이동에 곱해지면 안 된다: **REJECTED**. 네이티브가 명시적으로
  `parentWorld × local`을 수행하며 1285005에서는 오히려 퍼짐을 줄인다.
- 셀 인덱스 clamp가 잘못된 셀을 고른다: **REJECTED(현 데이터)**. clean 144,502키,
  minor 40,384키에서 범위 밖 인덱스가 각각 0개다.
- 베지어 시간핸들 clamp가 minor의 퍼짐을 만든다: **REJECTED(상관 없음)**.
  clamp 대상은 clean 1.190%, minor 0.046%로 minor에 편중되지 않는다.

[아직 모르는 것] r95의 UV 수축 복원과 r96의 ADVANCE 복원 뒤에도 사용자가 보는
`1285005`의 잔여 차이가 정확히 어느 파츠/프레임인지. 좌표계 전체를 바꾸는 것은
근거가 없으므로 현행 렌더러는 수정하지 않는다.

[다음 검증] r96 화면에서 잔여 이상 파츠를 다시 특정한 뒤, 해당 파츠의 UV 창·
정점색·알파·인스턴스 위상을 원본 프레임과 1:1로 비교한다.

[신뢰도] 행렬 합성 **CONFIRMED**(원본 네이티브) · 좌표계가 minor 원인 아님
**STRONG**(전수 분포 + 1285005 방향성).

## 46. 원본에 없는 UV repeat·쌍 스트립 경로를 제거 — 1285005의 핵심 차이

[확인된 사실] 원본 `AnimssCellPart::updateCell()`은 셀마다 원본
`TextureImage`의 전체 폭·높이를 읽고, 셀 사각형과 UV 이동·회전·배율로 네 정점의
UV를 직접 계산한다. `_t`/`_u` 셀을 새 텍스처로 합치거나 셀 단위로 좌표를 감는
분기는 없다. 텍스처 샘플러 역시 `GL_CLAMP_TO_EDGE`를 사용한다.

[근거] `libAll.so`의 `AnimssCellPart::updateCell()`(`0x3e94e2c`)에서
`BBTexSfBase::GetTextureWidth/Height()`로 페이지 크기를 얻은 뒤 계산한 UV 네 점을
동일 메시 객체에 기록한다. 바이너리 전체에는 `GL_REPEAT` 사용이 없고
`GL_CLAMP_TO_EDGE` 경로만 존재한다.

[웹과의 차이] 웹은 화면상 빈 창을 줄이기 위해 다음 세 예외를 후기에 추가했다.

- 이동폭이 1 이상인 부분 셀을 개별 셀 텍스처로 바꾸고 repeat
- `uv-wrap.json` 대상 파츠를 셀 단위로 repeat
- `_t`/`_u` 두 셀을 별도 스트립으로 합쳐 repeat

이 방식은 픽셀 통계상 빈 구간을 줄이지만, 원본 데이터가 의도적으로 시트의 빈
영역이나 이웃 셀을 훑는 동작까지 다른 그림으로 바꾼다. `1285005`는 `eff_t/u`,
`logo_eff_t02/u02`와 다수의 `_t/_u` 셀이 이 예외에 걸려 원본과 차이가 특히 컸다.

[처리] 세 예외를 기본 OFF로 바꾸고, 모든 UV 파츠를 원본 시트 페이지 +
`CLAMP_TO_EDGE` 경로로 복원했다. 전체 시트 repeat도 기본 OFF다. 실험 경로는
비교를 위해서만 남겼다: `__anssStrip=1`, `__anssCellRepeat=1`,
`__anssWrap=1`.

[경쟁 가설] 셀 단위 repeat가 더 자연스럽게 보이므로 원본도 내부적으로 반복할
수 있다: **REJECTED**. 원본 함수가 페이지 크기와 셀 rect를 직접 사용하고,
repeat 샘플러가 바이너리에 없다. 자연스러움은 원본 동작의 증거가 아니다.

[아직 모르는 것] 원본과 r97의 남은 픽셀 차이. 후보는 웹의 비표준 이음매 페이드,
가산 텍스처 휘도-알파 보정, 코너 정점색 행 순서다.

[다음 검증] 1285005에서 `eff_t/u`, `fan02`, 로고 광택을 원본 캡처와 프레임별로
대조한다. 차이가 남으면 위 세 후보를 네이티브 함수와 같은 방식으로 검증한다.

[신뢰도] 원본 UV 계산·clamp **CONFIRMED**(네이티브 디스어셈블) · 웹 예외가
1285005를 변경했다는 판정 **CONFIRMED**(런타임 분기와 테이블 직접 대조).

## 47. 반텍셀 보정 가설 철회 — 원본의 0.5는 쿼드 반폭·반높이

[확인된 사실] 원본 `updateCell()`은 셀 UV를 텍셀 중심으로 0.5px 안쪽에 넣지
않는다. `0.5` 상수는 UV 스케일을 중심 기준으로 적용하기 위한 `-scale/2`,
`+scale/2` 계산에 사용된다. 최종 UV에는 셀 시작점과 폭을 더한 뒤 텍스처 전체
폭·높이로 나누며 별도의 0.5px inset은 없다.

[근거] `0x3e95298`에서 `-0.5 * uvScale`, `0x3e952a4`에서 `+0.5 * uvScale`을
만들고 회전행렬로 네 모서리를 계산한다. 이어 `0x3e95334`~`0x3e9538c`에서 셀
좌표를 더하고 `GetTextureWidth/Height()` 결과로 나눈다. 픽셀 단위 `+0.5` 또는
폭 `-1` 연산은 존재하지 않는다.

[해석] r98의 `(x+0.5, w-1)` 처리는 분할된 셀 양쪽을 각각 축소해 원본에 없는
틈과 크기 차이를 만들 수 있다. 사용자가 느낀 “부드럽게 이어지지 않음”과 방향이
일치한다.

[경쟁 가설] 반텍셀 inset이 아틀라스 bleed를 막는다: 일반 렌더링 기법으로는
가능하지만 이 엔진의 실행 경로에는 없으므로 원본 재현 기준 **REJECTED**.

[처리] 상세 렌더러와 목록 아이콘의 UV를 다시 `x/W`, `y/H`, `w/W`, `h/H`로
복원했다. PNG/WebP 외곽이 모두 완전 투명이라는 측정만 유지한다.

[아직 모르는 것] 원본 엔진의 텍스처 업로드 단계에서 아틀라스에 별도 padding을
생성하는지 여부. 현재 `TextureImage` 원본 페이지를 직접 쓰는 경로에서는 근거가 없다.

[다음 검증] r100에서 분할 셀 경계와 전체 크기를 원본 캡처에 맞춰 비교한다.

[신뢰도] 반텍셀 가설 철회 및 정확한 UV 경계 **CONFIRMED**(전체 산술 경로 추적).

## 48. 원본 정점 번호까지 포함한 CHK 코너 순서 확정

[확인된 사실] 네이티브 `BBMsf` 쿼드의 정점 번호는 `0=TL, 1=BL, 2=BR,
3=TR`이다. CHK의 `c0..c3`는 목적지표 `{0,3,1,2}`로 기록되므로 의미상 순서는
`TL,TR,BL,BR`이다. 웹 메시 정점은 `TL,TR,BR,BL`이므로 `c0,c1,c3,c2`가
정확한 대응이다. RGB와 알파는 같은 네이티브 호출로 전달되며 순서를 나눌 근거가 없다.

[근거] `0x3e95138`, `0x3e95170`, `0x3e9517c`, `0x3e951b8`의 위치 네 쌍과
`0x3e95390`~`0x3e953e4`의 UV 네 쌍을 회전 0으로 전개하면 각각 TL, BL, BR,
TR이다. 정점색 루프 `0x3e951f4`~`0x3e95264`는 상수표
`libAll.so:0x1e7b4e0 = {0,3,1,2}`를 목적지 인덱스로 넘긴다.

[해석] r99는 상수표만 읽고 네이티브 정점 번호도 웹처럼 TL,TR,BR,BL이라고
가정해 `c0,c2,c3,c1`로 잘못 배치했다. 이전의 알파 전용 역순 임시처리도 원본과
다르다. 둘 다 `_t/_u`의 페이드 방향과 이음매를 훼손한다.

[경쟁 가설] RGB와 알파가 서로 다른 코너 규약을 쓴다: 동일 ARGB를 한 번의
정점색 호출에 전달하므로 **REJECTED**.

[처리] 메시 RGB·알파를 모두 `c0,c1,c3,c2`로 통일했다. 비메시 2×2 램프는
CHK 의미 순서 그대로 TL=c0, TR=c1, BL=c2, BR=c3로 생성한다.

[아직 모르는 것] 남은 차이 중 정점색과 무관한 가산 텍스처 변환·웹 전용
seam-fade가 차지하는 비율.

[다음 검증] 1285005의 분할 파츠를 레이어별로 확인하고, 다음에는 웹 전용
seam-fade와 가산 전처리를 네이티브 블렌드 상태와 대조한다.

[신뢰도] 정점 위치·UV·색 목적지 대응 **CONFIRMED**(한 함수의 전체 데이터 흐름).

## 49. 웹 전용 루프 이음매 페이드 제거

[확인된 사실] 원본 `[LOOP]` 재생 경로에는 끝·시작 경계의 알파를 점프 거리로
재계산하는 처리가 없다. 웹은 닫히지 않은 이동 트랙에 최소 2프레임에서 주기의
1/4까지 합성 페이드를 적용하고 있었다.

[근거] `evaluate.ts`의 `seamFade = jump/speed`와 경계 알파 곱은 웹에서 후기에
추가한 휴리스틱이다. CHK에는 해당 값이나 명령이 없으며 네이티브는 키프레임
알파와 `[LOOP]` 시계만 사용한다.

[해석] 서로 같은 위상으로 맞물려야 하는 `_t/_u` 및 인스턴스 파츠가 각자의
이동량에 따라 다른 시간 동안 어두워져, 원본에는 없는 맥동과 연결부 단절을 만든다.

[경쟁 가설] 순간이동을 가리기 위해 원본도 암묵적으로 페이드한다: 관련 상태값과
호출이 확인되지 않았고 소스 알파 트랙이 이미 존재하므로 **REJECTED**.

[처리] 드로어블에 곱하던 합성 seam fade를 제거했다. CHK가 저작한 알파와
마지막→첫 프레임 루프만 남긴다.

[아직 모르는 것] 원본 플레이어가 정확히 어느 렌더 틱에서 마지막 키를 포함해
감는지(길이 `L` 대 `L-1`)의 1프레임 차이.

[다음 검증] 1285005의 30fps 고정 프레임에서 분할 파츠 밝기 맥동이 사라졌는지
확인하고, 필요하면 네이티브 애니메이션 시계 함수의 경계 비교를 추적한다.

[신뢰도] 웹 페이드가 비원본이라는 판정 **CONFIRMED**.

## 50. `[EMITTER]#standard` 네이티브 재분석 — 개수·방출 영역 교정

[확인된 사실] 원본 `Animss6EmitterModel::buildStandard()`은 각 `[ANIME]` 파트의
USERDATA 정수만큼 하위 모델을 정확히 한 번 할당한다. `interval`과 참조
애니메이션 수명으로 복제 수를 늘리지 않는다. `rect`의 POSX/POSY는 영역 중심이
아니라 최소 좌표이고 SCALEX/SCALEY는 그 좌표에서 더해지는 양의 범위다.

[근거] `0x3ec0db8`에서 `[ANIME]` 파트의 `getUserDataInteger()` 결과를 읽고,
`0x3ec0dc4`~`0x3ec0dcc`에서 정확히 `count × 0x38` 바이트의 ModelWork 배열을
할당한다. `initModelWorkStandard()`의 `0x3ec12fc`~`0x3ec1324`는 위치를 각각
`rect.posX + URand × rect.scaleX`, `rect.posY + URand × rect.scaleY`로 만든다.

[해석] 이전 익스포터의 `ceil(life/interval) × count`와 최대 64개 제한은 원본에
없는 합성 규칙이었다. 또한 `pos + (rand-0.5)×size`는 영역을 폭의 절반만큼
음수 방향으로 밀었다. 그래서 파티클이 과밀하고 한쪽으로 크게 퍼졌다.

[경쟁 가설] `interval`마다 count개를 계속 추가 방출한다: 네이티브 할당 크기와
모델 배열 개수가 USERDATA count로 고정되므로 **REJECTED**. interval 설정은
standard 빌드의 필수 이름으로 조회되지만 이 버전의 생성 수 계산에는 쓰이지 않는다.

[처리] 익스포터를 정확한 count와 `min + rand×range` 위치식으로 바꾸고 L 효과
681개를 재추출했다. 101002는 파티클 루트가 종전 224개에서 원본 할당 수 54개로
교정됐다. back/front 역할은 이미터가 속한 원본 PRCT 파트를 그대로 유지한다.

[아직 모르는 것] 원본 전역 난수기의 최초 시드. 웹 아카이브는 재현 가능한
고정 시드를 사용하므로 분포와 개수는 같지만 매 실행의 개별 좌표까지 같지는 않다.

[다음 검증] 실제 `[EMITTER]` 효과의 밀도와 영역을 원본 캡처와 비교한다.
1151005는 `[EMITTER]`가 아니라 b1의 일반 애니메이션 파츠와 f1의 로고 파츠로
구성되므로 별도의 앞/뒤 합성 검증 대상으로 유지한다.

[신뢰도] 할당 개수·rect 난수식 **CONFIRMED**(네이티브 산술 경로) · 고정 시드
분포 재현 **STRONG**, 개별 난수 일치 **UNKNOWN**.

## 51. 인스턴스 하위 파츠의 안정 정렬 순서 복원

[확인된 사실] 네이티브의 priority 정렬은 같은 우선순위에서 기존 파츠 순서를
유지한다. 인스턴스가 참조한 하위 애니메이션은 그 인스턴스 노드의 자식이므로,
뒤에 오는 형제 파츠보다 먼저 방문된다.

[문제] 익스포터는 직접 노드를 전부 추가한 다음 인스턴스를 일괄 확장했다. 그 결과
하위 파츠가 원래 자리 대신 배열 끝으로 이동했고, 웹의 안정 정렬 tie-break가 이
잘못된 배열 인덱스를 사용했다. 1151005의 경우 `logo_eff01/02` 인스턴스는 파일상
`logo`보다 앞인데도, 웹에서는 모두 `logo` 뒤에 추가되어 광입자가 로고 앞으로
올라왔다.

[처리] 재귀 확장이 끝난 뒤 부모-자식 관계를 깊이 우선(pre-order)으로 다시 펴고
부모 인덱스를 재매핑했다. 명시적 priority 값은 건드리지 않으며, 같은 priority의
순서만 원본 트리 순회와 맞춘다. 효과별 이름이나 ID 예외는 없다. L 효과 682개를
이 규칙으로 재추출했다.

[검증] 1151005의 front 순서는 교정 후 `logo_shadow → logo_eff01×4 →
logo_eff02 → logo`가 된다. 이 파일에는 standard emitter가 없으므로 사용자가 본
“파티클이 모두 앞에 있음”은 이미터의 front/back 문제가 아니라 인스턴스 평탄화
순서 문제였다.

[신뢰도] 안정 priority 정렬은 **CONFIRMED**, 트리의 동일-priority 방문 순서
복원은 **STRONG**. 실제 원본 캡처와 프레임 단위 시각 비교는 계속 필요하다.
